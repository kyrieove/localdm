# 0007 平板可以发言：与电脑输入框走同一个发送入口

日期 2026-10-23。状态：设计已由用户逐条确认（见 [设计](../plans/2026-10-23-tablet-live-chat.md)），第一期尚未实现，真实 iPad 与安卓平板实测未做。本文件不含剧本正文、卡面或真相。

## 背景
ADR 0005 规定“平板同步公共对话和当前环节，只读；公共操作仍由电脑完成”。用户要平板上的玩家也能跟 AI 主持说话，并最终看到和软件一致的界面。

## 决定（第一期，用户逐条确认）
1. 改写 ADR 0005 的“只读”：平板可以**发言**；推进、揭秘、录入投票、压缩上下文、放出材料仍只能在电脑上做。
2. 平板底部固定一条输入条，可展开对话面板；看角色本和线索卡时也能发言。
3. 必须先认领角色才能发言，发出的话署名“【角色名】……”。未认领时发送键灰掉，提示“请先认领角色”。电脑输入框里的话仍不署名。
4. **平板发言和电脑输入框走同一个发送入口**（`HostViewModel.SendAsync` 与 `IsBusy`），平板服务里不另写发送逻辑。AI 回答或朗读时所有平板发送键灰掉，显示“主持正在回应”；不排队、不打断。
5. 单条最多 300 字；同一平板两次发送至少隔 2 秒。不加别的限制（局域网内防连点，不防攻击）。
6. 平板只用系统键盘输入；语音用键盘自带的语音输入。浏览器在局域网 http 下不能直接用麦克风，所以平板不做录音、不装自签证书。电脑端麦克风按钮（ADR 0006）不受影响。
7. 平板的话在电脑对话里显示为署名玩家消息，进 AI 对话记忆（`dm_conversations`）并存档，不新建第二套记忆。AI 回答仍由电脑音箱朗读，平板不播声音。
8. 平板发言走现有意图识别（`HostIntentRouter`），只到提案：说“进入下一环节”会在电脑出现待确认提案，平板显示“已提议，等电脑确认”。整句“压缩上下文”或 `/compact` 在平板上当普通话处理，不执行。
9. 平板上能点的只有“发送”和“停止朗读”。
10. 不做私聊：平板发的话和 AI 的回答全桌可见。身份就是平板认领的角色，以浏览器会话为准，不加密码。

第二期（完整界面镜像，数据取自只含公开内容的投影，不推送电脑屏幕）见 [ADR 0008](0008-tablet-ui-mirror.md)，不在本决定的实施范围内。

## 否掉的方案
- 平板录音：局域网 http 下浏览器不开放麦克风，要装自签证书才行，对玩家太重。
- 平板发言排队：违反宪章“不建立多人问答队列”。
- 平板直接执行推进或揭秘：违反宪章原则 III，状态操作仍需电脑确认。
- 在平板服务里另写一套发送逻辑：两条路径会各自维护忙碌状态，并发时会出现同时两个请求。

## 后果
- 宪章升为 7.0.0：平板由“只读”变为“可发言”，原则 IV 的设备边界不兼容变化。
- `HostViewModel` 的发送入口要能被平板服务安全调用并给出明确的拒绝原因（忙碌、未认领、过长、过频）；这是最容易出并发 bug 的地方，必须单独测试：两块平板同时发送、电脑与平板同时发送、AI 回答中途平板发送，都只能有一个请求被接受，其余被拒绝并给出明确文案。
- 平板消息进入模型上下文时是玩家发言数据，不获得系统权限；角色本、手册、真相、模型备忘仍不进平板聊天接口。
- 需同步改 `specs/001-local-dm-mvp/` 里写着平板只读的位置、`docs/user-guide.md`、`PRODUCT.md`。
- 重新验证：除自动测试外，必须用真实 iPad 和安卓平板（各自设备上可用的浏览器）实测，记录设备型号、系统、浏览器版本和实际结果；通过前不能说功能完成。
