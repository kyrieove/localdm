## 一、流程体验实测

### 角色 1 · 唐（操作者兼核心嫌疑人）

**1）搜证：108 张牌能不能逐一亮相 —— 不能，按钮是死的（P0）**

- 实测：`开始这一局`（第 1 次提交）→ `下一环节`（第 2 次，第 3 次）进入「搜证」的瞬间，右侧「已发放材料编号」**一次性亮出全部 10 个牌堆编号**（1楼51-55 / 回忆唐11-15 / 回忆杰6-10 / 回忆海1-5 / 回忆玉16-20 / 回忆舒21-25 / 地下室43-50 / 房间2楼36-42 / 抉择26-29 / 现场30-35），而「发放一个材料编号」按钮在同一帧就已灰掉。UIA 读到的按钮状态是 `enabled=False`，点不动。
- 根因（两处叠加，都是确定性代码）：
  - `Advance` 在换阶段时把下一阶段的材料**整批并入**已发放：[GameEngine.cs:99](src/LocalDm.Core/Game/GameEngine.cs#L99-L103)；
  - 按钮可用性只看「本阶段还有没有未发放编号」：[SessionViewModel.cs:154](src/LocalDm.App/ViewModels/SessionViewModel.cs#L154)，而搜证阶段的 10 个编号在进入时就已被并掉，`PendingMaterials` 恒为 0 → 按钮恒灰（[HostView.xaml:276](src/LocalDm.App/Views/HostView.xaml#L276-L278)）。
  - 也就是说：**「逐一亮相」变成了「一次全亮」，新按钮在真实剧本上从头到尾没有被按响过一次。**
- 同一问题的历史证据：仓库里更早的截图同样显示进入搜证即刻「已发放材料编号：线索包一、线索包二」、「待发放材料编号」为空（[docs/evidence/us3/05-material.png](docs/evidence/us3/05-material.png)），说明这不是我这次触发的偶发。

| 搜证阶段实测（第 3 次提交） | 结果 |
| --- | --- |
| 已发放编号 | 10 个牌堆，全部已发放 |
| 待发放 | 0 |
| 按钮 enabled | `False`（灰） |
| 讨论阶段再点发放 | 被引擎拒绝：`PHASE_CONDITION_UNMET / 本阶段原本不允许发放材料。` |

**2）互动提问：AI 得体且不剧透吗 —— 不剧透做到了，得体没做到**

搜证阶段实际送进模型的公开依据只有 3 行（探针打印原文）：

```
搜证
按剧本规定完成搜证
线索已按编号发放
```

因为 `BuildGroundingText` 只取「阶段标题 + 条件 + Public 段 + 已解锁真相」，既不含**已发放编号列表**，也不含卡牌正文：[HostNarration.cs:139](src/LocalDm.Core/Hosting/HostNarration.cs#L139-L165)。真机模型的实际回应：

- 问「我想知道凶案发生的时间」→「关于凶案发生的时间，目前公开内容里还没有，我现在不能说，也不能猜测。大家可以先查看已按编号发放的线索……」
- 问「现在可以公开什么线索」→「现在能公开的就是已经按编号发到你们手里的那些线索……我这边没有额外可补充的公开内容。」

结论：**绝对不剧透，答案是「空气里只有 3 行」，模型无从泄露**；但桌上 5 个人听到的是一句礼貌的空话——它连「已经发了哪 10 个编号」都不知道，不可能接住「现在可以公开什么线索」。且软件明确选择**不做输出审查**（[HostViewModel.cs:485](src/LocalDm.App/ViewModels/HostViewModel.cs#L485-L488)），一旦模型想出彩就会编时间、编线索，这条风险完全由提示词上下文承担（P1）。

### 角色 2 · 杰（隔桌 1.5 米对坐）

**1）远距观屏找实体牌：编号清晰，但「分组」信息不足**

- 10 个编号在 1320 宽窗口里 4 行排完，13px 白底卡片、编号含范围（如 `房间2楼36-42`），1.5 m 内读编号没问题；本轮**只在窗口尺寸下实测**，投影等比放大后的观感未实测。
- 不足：卡片只有编号，没有「几楼/几张」的直观分组与发放顺序；一次全亮 10 个编号，桌上等于同时拿到 108 张牌，无法按序对应到「唐刚发的这一堆」。

**2）大屏复盘：13:30~18:00 的 8 轨表格对齐严整吗 —— 不严整（P1）**

我按显示列宽（汉字记 2 列）逐行量了文本本身的列位：

| 部分 | 实测 | 判定 |
| --- | --- | --- |
| 表头 | 8 个名字散在 **7 行**上（玉书+玉馨 同行），起点列 5,12 / 13 / 18 / 22 / 26 / 30 / 34 | 不是表头行，是一段阶梯 |
| 表体 | 每行词元起点逐行漂移，例：`0,6,15,24,31,42,51` vs `1,7,19,28,44` vs `0,12,21,34,43` | 无固定 8 列网格 |
| 竖线/行首标签 | 无 | 空单元格无法辨识，只能靠目测推断 |
| 渲染 | `Consolas, Cascadia Mono, monospace` + `TextWrapping=NoWrap` + 双向滚动（[HostView.xaml:156](src/LocalDm.App/Views/HostView.xaml#L156-L162)） | 折行错乱确实治好了 |

真实窗口截图（[artifacts/accept-truth-board.png](artifacts/accept-truth-board.png)）里第一屏只看到「## 13:30~18:00的时间线」「```」和 7 行阶梯状人名，表体事件全在折叠线以下。**「不折行」是渲染层修复，「对齐」是数据层问题，这一项修复只走了半程。**

另外：Consolas 没有中文字形，汉字走字体回退，空格与汉字的进宽不是 2:1，投影放大后列位会继续漂移——这一条我按机制判断，未逐列像素量测。

### 角色 3 · 海（硬核挑刺船长）

**1）抗造：连点「发牌」会不会重复发 —— 按钮没得点，改用命令级注入加压**

- 真实按钮在搜证阶段不可用，所以「快速双击」在桌面上根本发生不了；这是可用的表现，但代价是功能缺失（见 P0）。
- 以工程手段压测同一路径：**同一 `expectedRevision` 并发发出两次命令 → 一次 `Committed`、一次 `Rejected / STALE_REVISION`**。护栏是三层：`Busy` 重入闸 + `ExpectedRevision` 乐观并发（[CommandDispatcher.cs:40](src/LocalDm.Core/Game/CommandDispatcher.cs#L40-L43)）+ 事务内复查 revision 与 receipt 唯一约束（[SessionStore.cs:142](src/LocalDm.Infrastructure/Storage/SessionStore.cs#L142-L152)）。
- 非搜证环节按钮严格灰显：讨论/投票/真相/复盘四阶段的 MaterialIds 均为 0，按钮 disabled；即便绕过界面直接发命令，引擎也拒绝（实测 `PHASE_CONDITION_UNMET`）。

**2）投票：A=3, B=2 录入顺手吗 —— 顺手，但录完看不到结果（P2）**

| 动作 | 实测 |
| --- | --- |
| 输入 `A=3, B=2` | 解析通过，`Total=5` 与 5 人局相符 |
| 未勾选「确认这是大家核对过的汇总」直接提交 | 拒绝：`CONFIRMATION_REQUIRED` |
| 勾选后提交 | `Committed`，进入第 5 次提交 |
| 揭秘复用投票勾选？ | 不复用，揭秘有独立勾选框（[SessionViewModel.cs:256](src/LocalDm.App/ViewModels/SessionViewModel.cs#L256)） |
| 提交后汇总回显 | **没有**。界面上没有任何 `VoteSummary` 绑定（`HostView.xaml` 全文无此绑定），只有输入框原文 + 「已提交：投票，revision=5」 |
| 宽松解析 | `A=3,B=2,C=0` 被接受（多出一个 0 票选项）；`A=3,B=1` 也解析通过，靠引擎按总人数兜底拦下 |

纸笔投票的口头节奏是「我念：A 三票、B 两票」，桌边需要的是**念完能看到一张确认卡**；现在念完只能看输入框里的自己敲的字，改录时也没有「当前已记录」的状态位。

### 角色 4 · 护士（隐私与防剧透）

**1）只显编号、正文 100% 隔离 —— 做到了**

- 卡牌正文全部是 `Private` 段（172 段），公共投影只带 `ReleasedMaterialIds`（[PublicSessionProjector.cs:47](src/LocalDm.Core/Game/PublicSessionProjector.cs#L47)），并有 `EnsureSecretFree` 防御性校验。
- 探针实测：搜证阶段把整个投影序列化成 JSON，**不含任何卡牌正文片段**（取卡牌正文中的 16 字片段做子串比对，结果为 False），也不含 Truth 字段、不含 5883 字真相的首段。
- 事件日志只记阶段/编号/票数（[CommandDispatcher.cs:98](src/LocalDm.Core/Game/CommandDispatcher.cs#L98-L108)），不落正文。
- 装配 108 张牌后并没有把「正文」顺手塞进任何新通道——这一条是**干净的**。

**2）5883 字真相展开 —— 内容完整，但呈现分两处、语法直接上屏（P2）**

- 揭秘后 `RevealedTexts` 有 4 段、合计 5883 字（显示层 5880 字 + 3 个换行），**无截断**。病历肆号、多重人格（阿杰/阿海、淑娥/舒望、玉书/玉馨）、贺世珍诱导他人杀死自己等核心诡计均在正文内。
- 但同一份真相同时出现在**右栏「已公开的揭秘」**（300px 宽、`Wrap`，ASCII 表被撕碎）和**左侧大屏**（`NoWrap`）；`##`、` ``` ` 与扫描页眉页码（07/08/09/10）直接上屏，没有做任何 Markdown 处理。

**3）断电恢复 0 次重播 —— 做到了，但 0 回显**

- 重启实测：恢复后 `SpeechState=Idle`（[SessionRecovery.cs:78](src/LocalDm.Infrastructure/Storage/SessionRecovery.cs#L77-L78)），不自动朗读、不自动补做操作，投票输入框为空，界面文案为「已恢复「孽岛疑云」进度至「复盘」（第 9 次提交）。」——**没有再出现「请勾选准备后开始」**（全文检索 `勾选` = False）。修复 3 成立。
- 但恢复后**看不见任何人投了什么**：`VoteSummary` 已从库里恢复，界面从不显示它（同 P2）。

## 二、隐私与防剧透审查

| 通道 | 内容 | 结论 |
| --- | --- | --- |
| 公共投影（UI 数据源） | 阶段、编号、票数、解锁后的真相 | 通过：无私有段、无未解锁真相 |
| 模型问答上下文 | 阶段标题 + 条件 + Public 段 +（已解锁）真相 | 通过：搜证阶段只有 3 行，卡牌正文永不进入 |
| 事件日志 | 类型、阶段流转、编号、票数合计 | 通过：无正文 |
| 输出侧 | 不做审查，模型回什么念什么 | **风险保留**：防护全在「上下文隔离」，无二层兜底 |

**审查意见**：以「只显编号」为验收标准，全部达标；以「绝对不剧透」为目标，当前达标但**依赖上下文为空**这一脆弱前提。一旦为了让 AI 接得上话，把「已发放编号 + 卡牌正文」塞进上下文，就会立刻从「不剧透」滑向「大范围剧透 + 无输出审查」。建议只加**编号**，永不加正文。

顺带一处文档漂移（不属本次三项修复）：`docs/project-state.md` 与 `specs/.../tasks.md` 都把 `PublicReplyPolicy` 记成已完成，但仓库里没有这个文件。

| 维度 | 评价 | 依据 |
