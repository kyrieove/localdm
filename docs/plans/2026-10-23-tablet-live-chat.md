# 平板实时对话与界面镜像（设计，2026-10-23 已与用户逐条确认）

状态：只有设计，**没有写任何代码**。本文件不含剧本正文、卡面或真相。
给下一次对话：先读本文件，再读 `docs/decisions/0005-tablet-distribution-by-card-name.md` 和 `docs/project-state.md` 末尾。

## 目标
平板上的玩家能像在软件里一样跟 AI 主持说话，并看到和软件一致的界面。

## 第一期：平板发言
1. 平板底部固定一条输入条，可展开对话面板，看角色本和线索卡时也能发言。
2. 必须先认领角色才能发言；发出的话署名成「【张三】……」。没认领的平板发送键灰掉，提示「请先认领角色」。
3. AI 回答或朗读时（软件的 `IsBusy`），所有平板的发送键灰掉，显示「主持正在回应」；不排队、不打断。
4. 单条最多 300 字；同一平板两次发送至少隔 2 秒。除此之外不加别的限制（局域网里防手滑连点，不防攻击）。
5. 平板只用系统键盘输入，想语音就用键盘自带的语音输入。浏览器在局域网 http 下不能直接用麦克风，所以不做录音、不装自签证书。电脑端的麦克风按钮（ADR 0006）不受影响。
6. 平板的话在电脑对话里也显示为署名玩家消息，进 AI 的对话记忆（`dm_conversations`）并存档，重启后还在；不新建第二套记忆。AI 的回答仍由电脑音箱朗读，平板不播声音。电脑输入框里的话仍不署名。
7. 平板发言走现有的意图识别（`HostIntentRouter`），但只到提案：说「进入下一环节」会在电脑上出现待确认提案，平板显示「已提议，等电脑确认」。整句「压缩上下文」/`/compact` 在平板上当普通话处理，不执行。
8. 平板上能点的只有「发送」和「停止朗读」。推进、揭秘、录入投票、压缩上下文都留在电脑。

## 第二期：完整界面镜像
1. 网页重做一份软件界面，布局和内容与软件一致，数据取自只含公开内容的投影（`PublicSessionProjector` 一路），实时刷新。**不推送电脑屏幕画面**：否则操作者打开设置页、导入向导、材料面板时，真相或备忘可能露给全桌；秘密要在业务投影处隔离，不能靠 UI 隐藏。
2. 主窗口左侧栏的「开始、推进、放出材料、提交投票、揭秘、结束、暂停/继续」（`src/LocalDm.App/MainWindow.xaml` 第 191–271 行）在平板上显示成灰色，旁边写「请在电脑上操作」。竖屏放不下时折叠成一行当前环节。
3. 备忘、上下文占用等内部状态不显示。

## 不变的
- 电脑端的对话、推进、揭秘、投票权力不变。
- 不做私聊：平板发的话和 AI 回的话全桌可见。
- 角色本、手册、真相、模型备忘永远不进平板的聊天接口。
- 平板身份就是它认领的角色，以浏览器会话为准，不加密码（延续「防误看即可」）。
- 模型回答是一次性返回（`IMagpieGateway.CompleteAsync` 返回完整字符串），没有边出字边显示；平板显示「主持正在回应…」，然后整条出现。
- 刷新或掉线后用已有的 `GET /tablet/public?after=N` 补拉历史，对话不丢。

## 要改的文档
- 新写 ADR 0007，改写 ADR 0005 里「平板同步公共对话，只读；公共操作仍由电脑完成」这一条。
- 宪章（当前 6.0.0，语音输入那次升的；若尚未提交以工作区为准）再升一个主版本，并写明：重新验证要求见下面的完成标准。

## 完成标准
- 真实 iPad 和安卓平板（不限定品牌，各自设备上可用的浏览器）实测通过，记录设备型号、系统、浏览器版本和实际结果。通过前不能说功能完成。
- 并发测试：两块平板同时点发送、电脑输入框和平板同时发送、AI 回答中途平板发送，都只有一个请求被接受，其余被拒绝并给出明确文案。

## 风险
一期要改软件里「一次只处理一个请求」的入口（`HostViewModel.SendAsync` 与 `IsBusy`），让平板发言和电脑输入框走同一个入口。这是最容易出并发 bug 的地方，要单独加测试，不要在平板服务里另写一套发送逻辑。
