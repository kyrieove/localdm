# 剧本库导入向导方案：在软件里导入新剧本，全程不剧透

日期 2026-10-21。状态为用户已确认需求，待实现。
基线代码：`main` 的 `44fbc8e`。前置方案：`docs/plans/2026-10-20-ai-dm-organizer-context.md`。

---

## 1. 需求（用户已确认）

- 剧本库要能**在软件里导入新剧本**：选一个剧本文件夹，软件完成识别、分类、生成流程、打包，导入后出现在剧本库里，可以开局。
  不再需要命令行，也不再需要手写 `script-flow.json`。
- **任何剧本都能用**：不认死目录名（现在的命令行工具只认"以'装订'结尾的目录"和"线索卡牌"目录），不认死页号，不认死剧本名。
- **材料分类**：软件先猜哪个文件夹是组织者手册、哪些是角色本、哪些是线索卡，导入的人逐个确认或改正。
- **流程环节**：AI 读组织者手册起草流程（环节、顺序、每环要做什么），并标出手册里哪些页是真相；导入的人确认或修改。
- **导入的人可能就是这局的玩家，所以导入全程不能剧透**：界面上不显示剧本正文、卡面、真相、缩略图，只显示文件夹名、页数、进度和不含剧情的流程信息。

---

## 2. 向导五步

| 步骤 | 界面显示什么 | 不显示什么 |
|---|---|---|
| ① 选文件夹 | 文件夹路径；剧本名输入框（默认取文件夹名）；玩家人数（4–6） | — |
| ② 分类确认 | 每个材料分组一行：分组名、相对路径、页数、文件类型、软件猜的类别（下拉可改）、猜测依据（例如"名称含'线索'"） | 任何图片缩略图或正文 |
| ③ 识别 | 总进度（第 N/共 M 页）、预计剩余时间、失败页数；可取消；再次导入时已识别的页直接复用缓存 | 识别出的文字 |
| ④ 流程确认 | AI 起草的环节列表：标题、类别、一句话提示、推进条件，可改、可删、可增、可调整顺序；手册分层摘要："组织者手册共 12 页：真相 4 页（第 8–11 页），不入包 2 页，其余为主持人专用页" | 真相页内容；任何剧情细节 |
| ⑤ 完成 | 就绪检查结果（能否开局、问题清单，只列问题类别和分组名）；"打开这一本"按钮 | — |

任何一步都可以返回上一步修改；③ 完成前关掉软件，下次导入同一文件夹时从缓存继续。

## 3. 具体改动

### 3.1 导入服务：把命令行里的流程搬进可复用的服务

**新文件**：`src/LocalDm.Infrastructure/Import/ScriptImportService.cs`

`tools/LocalDm.Probe/BuildPackageProbe.cs` 里的装配逻辑（预检、识别、建包、登记、写包文件）搬到这里，命令行和界面共用这一份实现。命令行改成调用它，原有参数保持兼容。

```csharp
public sealed class ScriptImportService
{
    /// <summary>扫描文件夹，找出材料分组并猜类别。不读文件内容，不跑识别。</summary>
    public ScriptScanResult Scan(string storyRoot);

    /// <summary>逐页识别。progress 每完成一页报一次；可取消；已识别的页走缓存。</summary>
    public Task<ScriptExtraction> ExtractAsync(
        string storyRoot, IReadOnlyList<ScriptGroup> confirmedGroups,
        IProgress<ImportProgress> progress, CancellationToken ct);

    /// <summary>按确认过的分类与流程建包、登记、写包文件。</summary>
    public Task<ScriptImportResult> BuildAsync(
        ScriptExtraction extraction, string title, int playerCount, ScriptFlow flow, CancellationToken ct);
}
```

`ScriptGroup`：`Name`（分组名，重名时用相对路径）、`RelativePath`、`Files`（已排好页序）、`PageCount`、`Kind`（`Organizer` / `Role` / `Material` / `Ignore`）、`GuessReason`。

#### 3.1.1 找分组（通用规则）

- 递归遍历剧本文件夹。**直接包含图片（jpg/jpeg/png/webp）或 PDF 的文件夹**算一个分组；一个独立的 PDF 文件也算一个分组（分组名取文件名）。
- 只有子文件夹、没有文件的中间层目录不算分组，只用来生成相对路径。
- 分组名默认取叶子文件夹名；同名时改用相对路径（用 `/` 连接），保证唯一。分组名用于段 ID，必须稳定。
- 页序沿用现有的 `PageOrderKey` 规则（数字升序，卡背紧跟正面），无法归类的排最后，不丢弃。
- 跳过隐藏文件、`Thumbs.db`、`.DS_Store`。

#### 3.1.2 猜类别

按分组名和相对路径里的关键词猜，**依据要写进 `GuessReason`**，界面上给导入的人看：

| 类别 | 关键词（任一命中） |
|---|---|
| 组织者手册 | 组织、主持、DM、手册、说明、真相、组织者、主持人 |
| 线索卡 | 线索、卡、搜证、抉择、回忆、记忆、地点、证物 |
| 角色本 | 其余所有分组 |

附加规则：
- 命中多个类别时，组织者手册优先，其次线索卡。
- 一个组织者手册都没猜到时，界面要求导入的人指定一个，不能跳过。
- 猜到多个组织者手册时，提示导入的人只保留一个。现有的分层规则只支持一个组织者手册分组，这次不扩展。
- 角色本分组数和玩家人数不一致时，在 ② 页提示，但不阻止。
- 删除 `BuildPackageProbe` 里 `EndsWith("装订")` 和 `"线索卡牌"` 的写法，以及 `--title` 的默认值"孽岛疑云"。

#### 3.1.3 识别工具的路径

- MinerU 可执行文件读 `ToolSettings.MineruExecutable`（已有字段），没配置时退回现在的默认路径。
- 备用 OCR 的 Python 解释器：`ToolSettings` 新增 `OcrPythonPath`，设置页加一个输入框；没配置时退回 `LOCALDM_OCR_PYTHON` 环境变量，再退回 `python`。
- 隐私预检（`MineruPrivacyPreflight`）、数据授权（`DataConsent`）沿用现有逻辑，没通过就停在 ③，并显示现有的脱敏原因。

### 3.2 AI 起草流程

**新文件**：`src/LocalDm.Core/Import/FlowDrafter.cs`（组装提示词、解析结果）

- 输入：组织者手册分组的全部页（页号 + 识别文字）、剧本名、玩家人数、线索卡分组名列表（只给名字）、角色本分组名列表（只给名字）。
- 用设置里的 model ID 调用模型，非流式。
- 要求模型**只输出 JSON**，结构对应 `ScriptFlow`：

  ```json
  {
    "layering": { "truthPages": [8,9,10,11], "ignoredPages": [7,12] },
    "steps": [
      { "stepId": "read", "title": "阅本", "kind": "Read",
        "hint": "拿到角色本，读到写着先不要翻页的地方为止。",
        "conditions": ["全员读完自己的部分"],
        "sourceRef": "组织者手册第 3 页",
        "offersOpeningSpeech": true }
    ]
  }
  ```

- 提示词要求（写进代码常量，全文如下）：

  ```
  你在帮一个剧本杀软件整理流程。下面是组织者手册的全部页面（含真相），读完后输出这本剧本的游戏流程。
  看到这份流程的人可能就是这局的玩家，所以：
  1. title、hint、conditions 只写流程和操作（阅读、调查、讨论、投票、揭秘、复盘该做什么），不写任何剧情、人物关系、线索内容、凶手、手法或结局。
  2. 不写任何角色的秘密，也不写只有读过真相才知道的名词。
  3. kind 只能是 Read、Intro、Search、Talk、Vote、Reveal、Review 之一；必须有且只有一个 Reveal 环节，Reveal 之后才能出现 Review。
  4. sourceRef 写成"组织者手册第 N 页"，N 是这一环在手册里的依据页。
  5. layering.truthPages 列出所有写着真相、凶手、作案经过、复盘答案的页；拿不准的页也算进去。layering.ignoredPages 只列封面、版权页、空白页、"后面是真相"这类警告页。
  6. 不要输出 publicPages。
  7. 只输出 JSON，不要任何解释。
  ```

- 解析与校验：
  - JSON 解析失败或校验不通过（`ScriptFlow.ValidationIssues` 非空、没有 Reveal、页号超出手册页数）→ 自动重试一次，把失败原因附在请求里。第二次仍失败，就显示"AI 没能起草流程"，并提供一份**空白**环节表让导入的人手填，不要套默认流程。
  - `layering.publicPages` 一律置空（即使模型输出了）。理由：AI 主持会自己讲开场，手册页不需要直接上公共屏幕；而导入的人看不到正文，没法确认某页能否公开。
  - `layering.organizerGroup` 由 ② 页确认的组织者手册分组名填入，不让模型填。

#### 3.2.1 剧透检查（显示给导入的人之前）

**新文件**：`src/LocalDm.Core/Import/FlowSpoilerCheck.cs`

- 对每一环的 `title`、`hint`、`conditions` 逐条检查：与真相页原文连续 7 个字以上相同，就判为可能剧透。7 字门限沿用 `DmMemoCheck` 校准过的值，两处共用同一个常量。
- 命中的条目不显示原文，改为显示"这条提示可能含剧情，已隐藏，请重写"，并要求导入的人重写或删除后才能继续。
- 检查只拦"照抄真相"，拦不住改写过的剧情。所以 ④ 页顶部要始终显示一行提示："流程由 AI 起草，如果你在提示里读到了剧情，请直接删掉那一条。"

#### 3.2.2 流程确认页（④）

- 每一环一行：标题（可改）、类别（下拉）、提示（可改）、条件（可增删）、依据页（只显示"手册第 N 页"，不显示内容）。
- 可增、删、上下移动。删掉唯一的 Reveal 环节时阻止并提示。
- 手册分层摘要只显示页数和页号范围（见第 2 节表格）。允许把某页在"真相 / 主持人专用 / 不入包"之间切换，但界面上不显示那一页的任何内容。
- 线索卡的发放（`materialIds`）这一步不让 AI 起草，也不在 ④ 页编辑，一律留空：调查时由 AI 主持指路，玩家自己翻实体卡（前置方案第 1.1 节）。
- 确认后，流程 JSON 和剧本包一起保存：`packages/<packageId>-<version>.flow.json`，以后可以从剧本库"重新整理流程"打开再改。
  改流程会得到新的包标识（现有内容指纹规则），旧存档仍绑定旧包，这是现有行为，不要改。

### 3.3 剧本库界面

**文件**：`src/LocalDm.App/ViewModels/LibraryViewModel.cs`、`src/LocalDm.App/Views/LibraryView.xaml`，新建 `src/LocalDm.App/ViewModels/ImportWizardViewModel.cs`、`src/LocalDm.App/Views/ImportWizardView.xaml`

- 剧本库顶部加"导入新剧本"按钮，打开向导（可以是剧本库内的一个切换视图，不必新开窗口）。
- 导入进行中回到剧本库时，列表里显示"正在导入：第 N/M 页"，点击回到向导。同一时间只允许一个导入任务。
- 导入完成后刷新剧本列表，新剧本出现在列表里；就绪检查不通过的显示"需要复核"和问题类别。
- 剧本列表每本多一个"重新整理流程"操作：跳到 ④（不重新识别），确认后生成新版本的包。
- 文案只说"组织者手册""角色本""线索卡"，不出现"真相页内容"之类的可点开入口。

### 3.4 宪章与文档

- 新增 `docs/decisions/0004-import-wizard-ai-drafted-flow.md`，写明：
  - 流程由 AI 依据组织者手册起草、人工确认结构，`sourceRef` 由 AI 标注、导入的人不核对正文。这是对宪章原则 I"流程必须有来源依据"的放宽，因为导入的人可能是玩家，看不到正文。
  - `publicPages` 一律为空的理由。
  - 剧透检查只拦照抄，拦不住改写。
- `.specify/memory/constitution.md` 原则 I 补一句："导入向导中的流程可由主持模型依据组织者手册起草，经人工确认结构后视为有来源依据。"按 Governance 一节的规则升次版本号（4.0.0 → 4.1.0）。

### 4.1 找分组与猜类别（`ScriptImportScanTests.cs`）

### 4.2 起草流程（`FlowDrafterTests.cs`，假 gateway）

| 用例 | 断言 |

- 用确认过的分类建包：`Roles` 数量等于角色本分组数，`Materials` 数量等于线索卡分组数，组织者手册不在两者里。
- 命令行 `--build-package` 改用服务后，对同一份测试文件夹生成的包与服务直接生成的包，段数和分组数一致。

## 5. 人工验收

1. 用《孽岛疑云》原始图片文件夹，**从界面**导入一遍：
   - ② 页的猜测是否正确：组织者手册 1 个，角色本 5 个，线索卡约 10 组。
   - ④ 页的流程是否合理，有没有读到任何剧情。
   - ⑤ 页显示能开局。
   - 和命令行生成的包对比：角色本分组数、线索卡分组数、真相页页号一致。
2. 中途在 ③ 取消，再重新导入，确认从缓存继续，没有重新识别已完成的页。
3. 如果手头有第二本剧本，再导入一遍，重点看目录结构不同时 ② 页猜得对不对、④ 页有没有剧透。
4. 导入后开一局，用前置方案第 5 节的第 1、4、6 条各问一次，确认 AI 主持拿到了手册和线索卡。

记录写进 `docs/evidence/us3/import-wizard-acceptance.md`，只记结论，不贴剧本内容。

## 6. 不在这次范围内

- 不支持多个组织者手册分组。
- 不做缩略图、正文预览、识别结果校对界面（会剧透）。
- 不让 AI 起草线索卡的分轮发放。
- 不改识别工具本身（MinerU、备用 OCR）和识别缓存的格式。
- 不改 AI 主持的提示词和上下文管理（前置方案的范围）。
