## 二、不依赖局域网：调研结论（2026-10-28）

### 本项目的真实用量（决定哪些免费档够用）
- 平板每 2 秒轮询一次，每次 2 个请求（`/tablet/catalog` + `/tablet/public`，`apps/tablet/lib/data/app_state.dart` 第 20、161 行起）。
  6 台平板玩 4 小时 ≈ 6 × 1800 × 2 × 4 = **约 8.6 万个请求 / 局**。
- 本机剧本包图片 807 张（`%LOCALAPPDATA%\LocalDm\assets`，只统计了文件大小）：中位 512 KB，90% 分位 1.3 MB，最大 4.5 MB，超过 1 MB 的 225 张。
  一名玩家翻完角色本（19 页）+ 手册（29 页）+ 9 张卡正反面 ≈ 66 张 ≈ 34 MB；6 人 ≈ **200 MB / 局**（App 有缓存会更少）。

### 候选对比
| 方案 | 免费？ | 要写的服务端代码 | 卡点 |
|---|---|---|---|
| **Cloudflare Quick Tunnel**（软件自带 `cloudflared`，起隧道得到 `https://随机名.trycloudflare.com`） | 是，不用账号 | **零**，现有接口和轮询原样能用 | 官方页（2026-09-30 更新）原文：仅供测试和开发、生产用命名隧道；无可用性保证；每条隧道最多 200 个在途请求，超出返回 429；不支持 SSE；每次创建地址都变。 |
| **Cloudflare 命名隧道**（同上，但用自己的域名） | 隧道免费，**域名约 10 欧/年** | **零** | 要买域名、域名托管到 Cloudflare。Cloudflare 正式支持的用法，地址固定。 |
| Cloudflare Workers + Durable Objects 自写中转 | 是 | 一个中转服务 + 把「HTTP 请求塞进 WebSocket」的协议 + 平板从轮询改推送 | 免费档 10 万请求/天，**现有轮询一局约 8.6 万，6 人长局会在中途超额失败**；每次调用 CPU 10 ms。必须先改成 WebSocket 推送。 |
| Supabase Realtime | 是 | 中转逻辑 + 图片另走存储 | 单条消息最大 256 KB，图片过不去；免费项目闲置 1 周自动暂停，隔周开局要手动恢复。 |
| Oracle 永久免费云主机 | 是（要绑卡） | 自写中转（可用 .NET） | 7 天内 CPU 和网络都低于 20% 会被回收——中转平时闲着，正好会被回收。 |
| ngrok 免费 | 是 | 零 | 每月 1 GB 出流量、约 2 万请求，一局就超。 |
| 付费小服务器（如赫尔辛基机房） | 每月几欧（推测，未查报价） | 自写中转或反向代理 | 要自己维护服务器。 |

结论：**最佳不是自写中转，而是隧道。** 隧道让电脑上的平板服务直接有一个公网 https 地址，现有接口、轮询、图片都不用改，服务端代码量为零；Workers 自写中转在免费档下还得先重写通信方式。

### 两条隧道路线（同一套代码，只差配置，待用户选）
| | Quick Tunnel | 命名隧道 |
|---|---|---|
| 费用 | 免费 | 只有域名钱：Cloudflare 注册商按成本价，`.com` 约 10.46 美元/年、续费同价（第三方价格站，2026-10-28 查；Verisign 11-01 涨批发价后约 11.17 美元）；`.cc` 约 8 美元。隧道本身免费。 |
| 地址 | 每次启动都变：软件中途重启，远程玩家要重新拿链接；App 存的地址每局失效 | 固定：可以直接写进 App，玩家打开 App 输房间码 / 口令就进，最像普通软件 |
| 官方定位 | 测试和开发 | 正式使用 |
| 主持人要做的 | 每局把新链接发给玩家 | 一次性：注册 Cloudflare、买域名、建隧道 |

两者服务端代码都是零；先做 Quick Tunnel 也不浪费，换命名隧道只改配置。
自写中转（Workers）只在要把软件发给很多陌生人用、需要账号体系时才值得做。

### 不管选哪种都必须做的
- **口令**：隧道地址是公网的，任何人拿到就能访问电脑上的平板服务。每次启动生成随机口令放进加入链接；所有 `/tablet/*` 和网页都核对口令，错了 401；连续错误限流。局域网也一起要求，不分两套。`cloudflared` 从本机连 `localhost:5188`，远程请求在服务端看来都来自 127.0.0.1：开隧道后任何代码都不能把「来自本机」当可信（2026-10-28 已 grep，`src/` 里平板服务目前没有按来源 IP 放行的逻辑）。口令也要挡住 Blazor 的 `_blazor` 连接和 `/app/` 静态文件。口令要送到：原生 App（存本机、每个请求带 `X-LocalDm-Token`）、网页版 `/app/`（从网址参数读）、Blazor 网页（核对后再发 Cookie）。
- **加入链接**：远程玩家扫不到电脑屏幕上的二维码。电脑平板面板加「复制加入链接」；App 手输框（`connect.dart`）和 `normalizeAddress` 要能吃下整条 https 链接并取出口令（现在只整理成 `host:port` 默认 http）。
- **`cloudflared` 随软件分发**：放进发布包，不让用户自己装；隧道起不来时面板说明原因，局域网照常可用。
- **远程玩家听不到电脑音箱**：AI 回答只在电脑朗读，远程玩家只看到文字；要听声音另做「平板播语音」（ADR 0012 待定项 1）。玩家之间说话另开语音通话。
- **登录**：链接 + 口令 + 认领角色已经能区分每个人；真要账号（换设备认人、历史记录）是另一件事，和「不依赖局域网」无关，可以以后再加。

### 谷歌登录（用户 10-28 追加要求）
ADR 0012 当时不做谷歌登录的原因是「局域网 IP 不能作为谷歌登录来源」。有了固定 https 域名，这个障碍就没了，但带来两个硬约束：
1. **必须用命名隧道**：谷歌要求预先登记回调地址（`https://<域名>/auth/google/callback`），不接受 IP，也不能登记每次都变的 `trycloudflare.com` 随机地址。所以选谷歌登录 = 选命名隧道（买域名）。
2. **App 不用原生谷歌登录 SDK，走网页登录**：原生 `google_sign_in` 在 iOS 上绑定 bundle ID；iloader 用每个人自己的免费 Apple ID 签名，bundle ID 可能被追加各自的 team ID 后缀（推测，依据是同类工具 isideload 的源码；装好后在 iPad 上看实际 bundle ID 验证），每台 iPad 都不一样，登记不过来。
   改用：App 打开系统浏览器登录页（`flutter_web_auth_2`，iOS 走 `ASWebAuthenticationSession`）→ 谷歌回调到电脑上的平板服务 → 服务端用 `Google.Apis.Auth` 的 `GoogleJsonWebSignature.ValidateAsync` 校验 ID token → 发本局会话凭证，经自定义 URL scheme 跳回 App。网页版 `/app/` 同一条流程。

要做的：
- 主持人一次性：建 Google Cloud 项目和 OAuth「Web 应用」客户端，登记域名回调；同意屏幕保持「测试」状态，把朋友的 Gmail 加为测试用户（测试状态上限 100 人，只要 `openid email profile` 不需要谷歌审核）。客户端密钥存电脑本机，不进仓库。
- 服务端：`/auth/google/start`、`/auth/google/callback`；电脑设置里维护「允许的谷歌账号」名单，名单外登录了也进不来——这就取代了口令。
- 身份落地：认领角色绑定到谷歌账号而不是设备编号，换平板、电脑重启后还能认回（顺带回答了「认领是否持久化」）。
- 隐私：电脑上会存朋友的邮箱和名字，只存这两项、存本机；公开发布时要写 GDPR 隐私说明。
